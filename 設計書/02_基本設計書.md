# 02_基本設計書

## 1. システム構成

読録は、Reactフロントエンド、Goバックエンド、PostgreSQL、Claude Haiku 4.5で構成する。ブラウザはGo APIへHTTP JSONリクエストを送り、Go APIがDB保存と必要最小限のAI呼び出しを制御する。

```text
Browser(React)
  ↓ fetch/JSON
Go HTTP Server
  ├─ Auth Middleware
  ├─ Note Handler
  ├─ Note Service
  ├─ AI Harness
  ├─ URL Extractor
  └─ Repository(database/sql)
        ↓
PostgreSQL(BOOK_notes)
```

## 2. 技術スタック

| 領域 | 採用技術 | 理由 |
| --- | --- | --- |
| Backend | Go標準ライブラリ中心 | HTTP、JSON、Context、SQLを理解しやすい |
| Router | `http.ServeMux` | 要件規模ではWebフレームワーク不要 |
| DB | PostgreSQL | 要件指定、Cloud SQLで利用可能 |
| DB Driver | PostgreSQLドライバ | `database/sql`だけではPostgreSQLへ接続できないため |
| Frontend | React | 要件指定、コンポーネント単位でUIを整理可能 |
| API通信 | `fetch` | ブラウザ標準で十分 |
| AI | Claude Haiku 4.5 | 要件指定 |
| GCP | Cloud Run + Cloud SQL | 小規模Webアプリとして単純な構成 |

## 3. アーキテクチャ

- フロントエンドは単一画面アプリとして一覧中心のUIを提供する。
- バックエンドはHandler、Service、Repository、AI Harnessに分ける。
- ServiceはAI失敗時のフォールバックとURL抽出を統括する。
- RepositoryはSQL実行だけを担当する。

## 4. フロントエンド構成

- `App`: 簡易ログイン状態と画面全体を管理する。
- `PasswordGate`: 簡易パスワード入力を扱う。
- `NoteEditor`: 新規作成・編集入力を扱う。
- `NoteList`: 記録一覧を表示する。
- `SearchBox`: 検索文字列を管理する。
- `MarkdownPreview`: 入力内容または保存内容を表示する。

React Routerは導入しない。単一画面で要件を満たすためである。

## 5. バックエンド構成

- `cmd/server`: 起動処理。
- `internal/http`: Router、Handler、Middleware。
- `internal/note`: Service、Repository、Model。
- `internal/ai`: AI Harness。
- `internal/config`: 環境変数読み込み。
- `internal/urlutil`: URL抽出。

## 6. DB構成

現時点のテーブルは`BOOK_notes`のみとする。

| カラム | 型 | 説明 |
| --- | --- | --- |
| `id` | BIGSERIAL PRIMARY KEY | 記録ID |
| `title` | TEXT NOT NULL | タイトル |
| `content` | TEXT NOT NULL | Markdown本文全文 |
| `urls` | TEXT[] NOT NULL DEFAULT '{}' | URL配列 |
| `created_at` | TIMESTAMPTZ NOT NULL DEFAULT now() | 作成日時 |

検索は`title ILIKE`または`content ILIKE`を使う。高度な全文検索は導入しない。

## 7. API概要

| Method | Path | 用途 |
| --- | --- | --- |
| `POST` | `/api/login` | 簡易パスワード確認 |
| `GET` | `/api/notes?q=` | 一覧取得・検索 |
| `POST` | `/api/notes` | 作成 |
| `PUT` | `/api/notes/{id}` | 編集 |
| `DELETE` | `/api/notes/{id}` | 削除 |
| `GET` | `/api/health` | ヘルスチェック |

## 8. 認証方式

`/api/login`で環境変数`APP_PASSWORD`と照合し、成功時にHttpOnly Cookieを発行する。Cookie値は環境変数由来のシークレットで署名する。これは本格認証ではなく、個人利用の簡易門番である。

## 9. AIハーネスの役割

AI HarnessはAI API呼び出し、タイムアウト、JSONレスポンス検証のみを担当する。URL抽出はGo側で行い、AIレスポンス内URLは保存判断に使わない。

## 10. AIとのデータフロー

1. ユーザーが自由入力を送信する。
2. Go側でURLを抽出する。
3. 明示タイトルがある場合はGo側でタイトルを確定する。
4. 必要な場合のみAIへタイトル生成とMarkdown構造化を依頼する。
5. AIレスポンスの本文が原文を欠落・改変していないか検証する。
6. 検証失敗時は原文またはGo側の最小Markdown化を保存する。
7. DBへ`title`、`content`、`urls`を保存する。

## 11. GCP構成

- Cloud Run: Go APIと静的フロントエンド配信、またはGo APIのみ。
- Cloud SQL for PostgreSQL: `BOOK_notes`を保存。
- Secret Manager: `APP_PASSWORD`、AI APIキー、DB接続情報を管理。

## 12. 画面構成

- 簡易パスワード画面
- 一覧中心画面
  - 新規入力欄
  - 検索欄
  - 記録一覧
  - 編集・削除操作

## 13. 技術選定理由

標準的で理解しやすい構成を優先する。GoではWebフレームワークを使わずHTTPの基本を明示する。ReactではReduxやRouterを使わず、コンポーネントとstateの基礎を確認できるようにする。

## 14. 採用しない技術と理由

| 技術 | 採用しない理由 |
| --- | --- |
| Gin/Echoなど | `net/http`で要件を満たせる |
| Redux | 状態が少なくReact標準で十分 |
| React Router | 単一画面で十分 |
| Elasticsearch | 小規模個人検索には過剰 |
| タグ・カテゴリDB | 入力負担とDB複雑化を招く |
