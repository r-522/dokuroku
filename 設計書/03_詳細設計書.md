# 03_詳細設計書

## 1. Backend詳細

### 1.1 ディレクトリ構成

```text
backend/
├── cmd/server/main.go
└── internal/
    ├── ai/
    ├── config/
    ├── http/
    ├── note/
    └── urlutil/
```

### 1.2 Router

`http.ServeMux`を使用する。`/api/notes`はメソッドで分岐し、`/api/notes/{id}`相当はパス文字列をGo側で解析する。ルーティングの仕組みを理解するため、外部Routerは使わない。

### 1.3 Handler

HandlerはHTTPの責務に限定する。

- JSON decode/encode
- Cookie確認
- Path/query取得
- HTTPステータス返却
- Service呼び出し

### 1.4 Service

Serviceはユースケースを担当する。

- 作成時にURL抽出を行う。
- 明示タイトルを判定する。
- 必要に応じてAI Harnessを呼ぶ。
- AI失敗時のフォールバックを行う。
- Repositoryへ保存する。

### 1.5 AI Harness

AI HarnessはClaude Haiku 4.5 APIを呼び出す境界である。`context.WithTimeout`でタイムアウトを設定し、レスポンスJSONを検証する。AIエラーはServiceへ返し、Serviceが本文保存を継続する。

### 1.6 Repository

`database/sql`を使い、SQLを明示的に記述する。Repositoryは業務判断を持たず、CRUDと検索だけを担当する。

### 1.7 DB接続

`DATABASE_URL`から接続し、起動時に`PingContext`で接続確認する。マイグレーションはフェーズ2で単純なSQLファイルとして用意する。

### 1.8 Context

- HTTP request contextをDB処理とAI処理へ渡す。
- AI処理のみ短いタイムアウトを設定する。
- DB保存はAI失敗と分離し、可能な限り継続する。

### 1.9 エラー処理とHTTPステータス

| 状況 | ステータス |
| --- | --- |
| 未認証 | 401 |
| 空入力 | 400 |
| JSON不正 | 400 |
| 対象なし | 404 |
| DB障害 | 500 |
| 正常作成 | 201 |
| 正常更新/削除 | 200または204 |

AI失敗のみで作成APIを失敗させない。保存成功時は201を返し、レスポンス内に`ai_fallback: true`を含める。

### 1.10 JSON処理

リクエスト例:

```json
{"raw_text":"# GoのHTTP\nHandlerについて理解できた。\nhttps://go.dev/"}
```

レスポンス例:

```json
{
  "id": 1,
  "title": "GoのHTTP",
  "content": "Handlerについて理解できた。\nhttps://go.dev/",
  "urls": ["https://go.dev/"],
  "created_at": "2026-08-13T00:00:00Z",
  "ai_fallback": false
}
```

## 2. Frontend詳細

### 2.1 コンポーネント構成

```text
frontend/src/
├── App.jsx
├── api.js
├── components/
│   ├── PasswordGate.jsx
│   ├── NoteEditor.jsx
│   ├── NoteList.jsx
│   ├── NoteItem.jsx
│   ├── SearchBox.jsx
│   └── MarkdownPreview.jsx
└── styles.css
```

### 2.2 State管理

`useState`と`useEffect`のみを基本とする。管理する状態は、ログイン済みか、入力本文、一覧、検索語、編集中ID、エラー、保存中フラグに限定する。

### 2.3 API通信

`api.js`に`fetch`ラッパーを置く。Cookie認証を使うため`credentials: "include"`を指定する。HTTPステータスを確認し、失敗時はUIに短いメッセージを表示する。

### 2.4 Markdown入力・プレビュー

入力はtextareaで行う。Markdownプレビューは必要最小限のMarkdown parserライブラリを使う。採用理由は、Markdownを安全かつ一貫してHTML表示するためであり、文章保存自体には影響させない。

### 2.5 一覧表示

表示項目はタイトル、登録日、本文プレビュー、URL有無、編集・削除ボタンに限定する。プレビューはフロントエンド表示上のみ短縮し、DB保存内容は短縮しない。

### 2.6 編集・削除・検索

編集は一覧上でtextareaを開いて行う。削除は確認後にAPIへDELETEする。検索は`GET /api/notes?q=`で実行し、高度な検索構文は提供しない。

## 3. DB詳細

### 3.1 テーブル定義

```sql
CREATE TABLE BOOK_notes (
  id BIGSERIAL PRIMARY KEY,
  title TEXT NOT NULL,
  content TEXT NOT NULL,
  urls TEXT[] NOT NULL DEFAULT '{}',
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_BOOK_notes_created_at ON BOOK_notes (created_at DESC);
```

### 3.2 カラム制約

`content`は空白のみを禁止する。`created_at`はDB defaultで設定する。更新日時は現時点の基本情報に含まれないため追加しない。

## 4. AI詳細

### 4.1 AIの責務

- 明示タイトルがない場合の短いタイトル生成。
- 自由入力をMarkdownとして扱いやすい形に整える。
- JSON形式で返す。

### 4.2 AIに渡す入力

- ユーザーの原文全文。
- 「本文を省略・要約・改変しない」制約。
- 「URLを追加しない」制約。

### 4.3 システムプロンプト方針

AIには、本文を編集せず、入力に存在する文を保持し、タイトルとMarkdown本文をJSONで返すよう指示する。明示タイトルがある場合はアプリケーション側で確定済みのため、AIに変更させない。

### 4.4 JSON Schema

```json
{
  "title": "string",
  "content": "string"
}
```

URLはSchemaに含めない。URL保存はGo側の抽出結果のみを使う。

### 4.5 レスポンス検証

- `title`が空なら`無題`にする。
- `content`が空、または原文の主要部分が欠落している場合はAI結果を破棄する。
- URLがAI本文内に追加されていても保存URLには使わない。
- 明示タイトルがある場合、AIタイトルは無視する。

### 4.6 タイトル決定

1. 原文先頭のMarkdown H1を明示タイトルとして採用する。
2. 明示タイトルがない場合はAIタイトルを採用する。
3. AI失敗時または空タイトル時は`無題`を採用する。

### 4.7 Markdown構造化

AIによるMarkdown化は、段落や見出しの構造化に限定する。本文の語尾修正、要約、言い換えは禁止する。検証で不安がある場合は原文をそのまま保存する。

### 4.8 URL処理

URL抽出はGo側の正規表現または`net/url`検証で機械的に行う。抽出対象はユーザー入力に存在する`http://`または`https://`の文字列のみとする。

### 4.9 AI失敗時の処理

- 作成処理は中断しない。
- titleは明示タイトルまたは`無題`にする。
- contentは原文または明示タイトル行を除いた原文を保存する。
- urlsはGo側抽出結果を保存する。
- レスポンスに`ai_fallback: true`を含める。

### 4.10 タイムアウト

AI処理は`AI_TIMEOUT_SECONDS`で制御し、未設定時は短い既定値を使う。タイムアウト時はAI失敗としてフォールバックする。
